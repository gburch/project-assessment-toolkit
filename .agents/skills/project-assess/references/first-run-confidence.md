# First-run evidence and confidence

Aim for defensible medium-or-better judgments in every applicable dimension on
the first Deep assessment. Confidence is earned through relevant inspection;
source collection, completed form fields and parser counts do not assign it.
Unknown, unsupported or inaccessible scope remains explicit.

Start with `evidence-query ID --view review-plan`, optionally selecting
`--dimension documentation|operability|extensibility|performance` or another
dimension. Page through `next_offset`; the response contains dimension scope,
source-context tasks and captured import connections. Deep selects a broader,
bounded set across roles and areas. Source identity binds the record; filenames,
syntax signals and historical co-change still need semantic inspection.

Follow the named change/upkeep questions through real callers, contracts,
configuration, relevant tests and guidance. Record actual edits, verification and
inspection separately. Inspect a favorable or simpler path as counterevidence.
Keep important unexamined areas and parser limits visible. Revisit weak dimensions
using these targeted tasks before finishing; stop when the supported scope is
adequate or the remaining material blocker is explicit. PAT does not invoke an AI
reviewer or execute the project to complete this pass.

For documentation, reuse captured sections, passage overlap, source references and
literal manifest-script comparisons. Trace which guidance a real code/config
change requires updating. Boilerplate, generated prose and word counts alone do
not demonstrate upkeep.

For operability, trace detection, diagnosis and recovery through state ownership,
manual work and runbook/code agreement. For extensibility, follow an existing
relevant variant through contracts, registration, configuration and verification.
For performance, follow an important data/request path and the work of maintaining
queries, bounds, caches, locks or tuning. Implemented controls do not prove current
recovery success or workload headroom.

Measurement evidence does not require permanent benchmark machinery. Establish a
user-relevant workload or risk first; existing observations or occasional advisory
measurements may suffice. Inspect timing gates for ordinary variance, margin and
rerun/baseline upkeep. Syntax alone cannot prove flakiness, and an unmet capability
target does not justify disproportionate assurance work.

Deep also reads bounded local first-parent Git metadata. It retains commit/date
and currently captured paths, not authors, messages, patches or target code.
Co-change is historical navigation, not required edits, elapsed effort or recurring
cost. Shallow boundaries, missing history and removed/uncaptured paths stay gaps.
Existing supplied operational/workload/cost reports retain their original source
identity and scenario limits; no new checks or services are run automatically.

## Medium source estimates

Fresh templates declare `methodology.confidence_standard: source-estimate-v1`.
Keep their unknown scores and low placeholders until the work is done. A medium
`burden_basis: source_estimate` uses the existing `burden_support` object:

- Explain the `claim`, `scope`, `scope_description`, `representativeness`,
  `counterevidence`, `freshness` and `limitations` against the selected anchor.
- Reference actual `change_trace_ids`; label every step's activity and cite current
  source examined for this dimension. A checkpoint is not automatically an edit.
- Add `corroboration_ids` and `counterevidence_ids`, citing inspected source in both
  the rating and its dimension coverage. They can refer to different behavior in
  one file when appropriate; no file-count quota establishes representativeness.
- `observation_ids` can be empty for a structural estimate. Do not invent timing,
  recurrence or testimony to fill them.
- Project scope needs reviewed representative dimension breadth and no unresolved
  material collection blocker. Workflow scope can remain partial and must not be
  presented as confidence in the whole project.
- Complete a distinct reviewer's exact-draft challenge including this dimension in
  `challenge.burden_dimensions`. The challenger checks actual semantic relevance,
  plausible contrary paths and the scope of the estimate.

PAT checks these support prerequisites, never automatically promotes a rating or
certifies the judgment. Older reviews retain their original confidence and lack
of this newer support declaration. High observed burden still requires applicable
experience or cost observations and the stronger recurrence/scope requirements.

Read `confidence_assessment.dimensions[D].coverage` for located omissions and
analysis limits. An oversized image and an omitted state owner have different
implications. Dependency-lock omissions still limit dependency/reproducibility
claims even where a source workflow can be inspected. Never mark an entire project
reviewed merely because a particular collection blocker is immaterial.
