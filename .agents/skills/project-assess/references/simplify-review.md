# Focused simplification review

Use the doctor's captured reuse, quality and efficiency candidates to identify useful changes, not to maximize findings. For recent-work review, focus on the user's changed paths or supplied diff and relevant callers. Exclude generated/vendor output and mechanical lockfile churn unless included in the request. For a whole-project assessment, map the important production workflows, inspect representative costly paths and record unexamined areas and collection limits. Do not let a previous test-only task or capped lead list define the whole scope. Sampling can support a qualified diagnosis; it cannot establish that unexamined areas are healthy.

## What to inspect

- **Reuse:** search nearby utilities, shared modules and tests before proposing another helper. Compare actual responsibilities, error handling and trust boundaries. Normalized duplicate bodies are structural similarity, not proof of interchangeable behavior.
- **Quality:** trace redundant state, brittle contracts, unnecessary delegation and unclear control flow. Dependency cycles need import timing and caller context; function-local imports may deliberately avoid initialization cycles. Mutable defaults or broad exception handlers need behavioral investigation before recommending a change.
- **Efficiency:** trace repeated reads/computation, broad loads, missing cleanup and hot-path work. Distinguish measured cost from source inference. Repeated authorization, freshness or concurrency checks may protect different moments; preserve their purpose. Parallelism requires compatible ordering, failure and transaction semantics.

For each credible finding, cite the captured location and explain the concrete cost or failure risk. Group related symptoms into ranked root-cause initiatives with the complete scope, target outcome, affected dimensions, acceptance evidence, burden effect and dependencies. Then identify a first slice and its closest verifier. A large responsibility can need procedural decomposition across real callers; do not reduce the plan to a small cosmetic edit simply because that proof is easy. Prefer an established local API when it preserves the required behavior. An extraction is useful when it simplifies real callers, not merely when it lowers a complexity count.

Before changing a shared function, route, type, export or public string, search direct and dynamic references, re-exports, tests and mocks. Distinguish unreachable statements from unused candidates. Account for package entry points, public exports, configuration, registries, reflection, plugins and external consumers where applicable. Absence from a local search does not prove disuse. Delete only with adequate evidence and preserved contracts; otherwise describe the uncertainty and a proportionate investigation. Never execute assessed code merely to resolve a read-only review lead.

Imported Ruff diagnostics are supplied, source-unverified leads. Match them to the captured source before using their locations; suggested fix applicability does not establish behavioral safety or authorize application.

For ecosystem fit, inspect both directions: replace repeated custom plumbing with an appropriate maintained library, or remove framework/dependency setup whose cost exceeds a utility's demonstrated needs. Compare migration, security, compatibility and ongoing upkeep, then name the smallest experiment and its verifier. Dependency counts and framework names alone establish neither excess nor a safe replacement.

## When fixes are authorized

A request for assessment or doctor output authorizes advice. When implementation is also authorized, apply high-confidence changes within that scope. Preserve outputs, error handling, permissions, source/evidence identity, transactions, concurrency and required performance properties. Use focused lint, type, unit or integration checks while iterating; before completion or an authorized push, inspect the full diff and complete required repository checks plus affected system and contract verification. Report results and gaps. A focused pass is not full validation, and missing execution evidence is not proof of missing tests. A suspected behavior bug needs explicit treatment as a bug fix, not a claim of behavior-preserving simplification.

Keep meaningful security, injection, isolation and domain boundaries. Avoid clever one-liners, line-count targets, generic plugin frameworks and broad helper merges. Defer uncertain changes whose proof cost exceeds their value, but retain important unresolved risks in the diagnosis rather than silently discarding them. No fixed number of review passes, findings or subagents is required.
