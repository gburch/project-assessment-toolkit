# Evolve toward the full target state

Evolve projects saved judgment and selected goals; it does not generate a diagnosis, validate effectiveness or assign scores. Read the actual rationale, recommendations, findings and coverage before choosing work. Keep critical and high findings visible even if all numeric targets are met. A review without an authored plan needs a roadmap, not generic advice disguised as a completed one.

For a whole-project assessment, explain the important system strengths, root causes, risks and unknowns across the eight dimensions. Inspect representative production workflows and boundaries, not only tests or the first available static candidates. Summarize what was examined, what remains unexamined, collection limits and current validation. Distinguish a missing protection from missing evidence of an existing protection. A focused review can remain focused when labeled; it must not imply whole-project coverage.

Use the brief's `dimension_inputs` directory to route shared scanner evidence to each dimension and see checks the tool does not perform. Page the complete `areas` and `area-dependencies` evidence-query views; the compact system map and challenge index are bounded starting points. Establish which omitted areas matter to each judgment, inspect representative source and relevant callers, and disclose the remaining scope. Raw source availability, a parser row, a control-like name and an imported report are different inputs; none alone establishes an effective control, a score or actual review depth.

Describe the complete intended target state and rank initiatives by risk, value, dependencies and recurring cost. Group related symptoms into root causes, including initiatives spanning dimensions. An initiative may require a substantial procedural decomposition or consolidation across real callers; low burden does not mean restricting every recommendation to a tiny edit. Preserve necessary authority, transaction, recovery and integration boundaries. Prefer adequate local functions, configuration, injection or supported APIs over speculative plugin frameworks. Do not force a quota of findings, initiatives, tests or rubric steps.

Each initiative must state the actual scope and acceptance evidence needed to reach its intended outcome. Identify its expected added, removed and retained upkeep against the selected burden ceiling. Then choose a first implementation slice that tests the approach without pretending to complete the full initiative. If both capability and burden miss their goals, plan both improvements and surface a genuine tradeoff. Retain useful capability above the minimum; a high score is not a reason to prune it.

## Optional structured review fields

Keep the template's existing identity, eight ratings and findings. Add these fields to the review JSON when reporting coverage and a roadmap; all evidence IDs must belong to that snapshot. Empty initiative lists are valid when no change is justified. Numeric ratings still require independent evidence-backed judgment.

- `coverage`: `schema_version: 1`, `scope: "whole_project" | "focused"`, `examined: [{area, evidence_ids}]`, `unexamined: [{area, reason}]`, `limitations: [string]`, and `validation: [{check, status, evidence_ids}]`. Validation status is `passed`, `failed`, `not_run` or `unavailable`. Examined areas and completed checks must cite evidence; explain supplied reports' source-binding limits. Replace the template's placeholder rather than treating it as completed coverage.
- Optional `coverage.dimension_reviews` maps every dimension to `{status, rationale, evidence_ids}`. The template starts unreviewed. Whole-project numeric judgments require reviewed or partial source-cited scope; focused reviews and legacy records retain their declared limits. The shared `review_coverage` summary makes breadth visible without certifying judgment quality.
- `plan`: `schema_version: 1`, `diagnosis`, `target_state`, and reviewer-ranked `initiatives`. Bind selected goals using optional `goal_revision`; alternatively, optional `assumed_targets` supplies all eight `{capability_min, burden_max}` pairs. Without saved goals this is only a proposed scenario, never an instruction to save goals. Neither binding is mandatory to preserve useful advice, but an unbound plan remains unconfirmed. If either supplied binding differs from current goals, review the plan before treating it as current.
- Each initiative: `id`, `title`, `priority` (`critical`, `high`, `medium`, `low`), `root_cause`, `scope`, `dimension_impacts` (dimension names mapped to intended effects), `evidence_ids`, `acceptance` (observable outcomes), `burden_effect`, `depends_on` (initiative IDs), and `first_slice`. IDs must be unique and dependencies must form an acyclic graph. Explain desired effects without promising automatic score changes.

Evolve preserves these fields under `goal_alignment` together with per-dimension rationale and recommendations, all findings and `urgent_findings`. `planning_status` distinguishes a missing review, missing plan, unconfirmed scenario, changed targets, incompatible rubric and a plan bound to selected targets. `ready` means the bindings match, not that the goals are achieved or that the plan has been independently validated. Legacy reviews remain valid and lack this extra context explicitly.

## Freshness, change traces and independent challenge

Use `review-template ID --mode fresh|refresh` to opt into `methodology` version 1. Set `reviewer_id` to the actual author and mark every dimension `reassessed`, `carried_forward` or `unreviewed`. A fresh review cannot carry judgments forward. A refresh may carry unchanged scores, confidence and burden basis from `based_on_review_id` only when source revision, manifest, collection scope and rubric match; cite evidence in the current snapshot. Changed source needs reassessment. Unknown dimensions remain unknown. Omitting methodology preserves legacy compatibility and makes freshness unestablished.

Add bounded `change_traces` with unique `id`, `title`, ordered `steps: [{owner, change, evidence_ids}]`, `cost`, `invariant`, `counterevidence` and `gaps`. Each step can include `activity: edit|verification|inspection|unknown`; omitted activity stays unknown. Separate actual required edit sites from read/dependency checkpoints. The activity is an authored declaration, not a verified edit count; a costly verification wait may require no edit. Trace valuable changes through actual callers, state owners and failure boundaries. Explain necessary coordination as well as avoidable friction. One trace can suffice for a small utility; a large system needs representative coverage of its important risks. At least one cited trace is required for a completed fresh whole-project review, but the tool cannot establish representativeness mechanically.

For burden, follow a meaningful change through both focused iteration and its required completion path. Account for setup, queue/feedback waits, security rework, reruns and recovery, with frequency and scope. A documented fast path is counterevidence, not proof of achieved cost. Record attributed maintainer experience and reconcile it with tool/history evidence; do not relabel a report as an independently measured run or demand a stopwatch before recognizing experienced friction. Necessary protection still counts toward upkeep. Large historical modules are leads for tracing ownership and edit propagation, not reasons either to assign a high score automatically or to dismiss the concern. The challenge should test both overstatement and unjustified optimism.

Complete the authored draft, then run `challenge-template ID --input draft.json`. This read-only operation returns snapshot identities, rubric, goals, system map, evidence navigation and authored traces without the draft's grades, rationale or plan. Give that packet to an independently reasoning agent or human, with access to captured source. Ask it to inspect representative paths, challenge omissions and alternative explanations, and identify justified complexity. Do not feed earlier grades or ask it merely to endorse the author. A focused Doctor check does not replace this broad challenge.

For whole-project score or recommendation confidence, record the critic's independent source view first, then let it inspect the exact authored draft, including ratings, rationales and recommendations. This follow-up can catch inconsistent scopes and unsupported burden anchors without anchoring the initial view. State which fields were actually inspected and which remain unseen; agreement does not replace evidence or automatically raise confidence.

The final `challenge` records version 1, status `completed`, its distinct `reviewer_id`, `independence: declared`, the packet's `draft_digest`, inspected `evidence_ids`, `summary`, `gaps` and bounded `items`. Each item has a unique `id`, `concern`, captured `evidence_ids` and a `response` containing `decision: accepted|rejected|deferred`, rationale and evidence. An empty concern list can be honest; it still needs inspection citations. Completed describes a review pass, not repaired code or proven correctness. Identities declare independence; PAT does not authenticate the reviewer.

The digest binds the complete authored draft, including its scores, coverage, plan and traces, to the captured snapshot. Formatting does not change it. Responses inside `challenge` do not change it. If the author changes substantive draft content after challenge, generate a new packet and obtain a bounded follow-up from the critic on the amended draft before submitting. Do not reuse a stale challenge digest. If a second reviewer is unavailable, use status `unavailable` with explicit summary and gaps; the assessment stays provisional. Full reports retain traces and responses; brief views show compact freshness and challenge labels.

## Confidence support

High confidence should name a proposition and the evidence that could disprove it. Keep severity independent: a high-confidence source fact can have low impact, and a serious possible failure can remain uncertain. Do not turn a finite source conclusion into proof of actual runtime behavior, measured upkeep or a whole-project rubric level.

An optional finding `support` contains `confidence: low|medium|high`, `scope: source|inference`, `rationale`, `counterevidence`, `limitations: [string]` and `citations: [{evidence_id, line, end_line, excerpt}]`. Obtain exact redacted spans with `source-context ID EVIDENCE_ID --line N --end-line M --max-chars 4000`; copy the four citation fields. Include every citation's ID, including counterevidence, in the finding's existing `evidence_ids`. A source contradiction usually needs the rule and its real caller/composition seam, not just a matching name. Record justified controls, unsupported callers and conditions that limit the conclusion.

PAT verifies full-file snapshot digests and exact redacted spans when preparing the challenge and submitting the review. Bounds are four spans per finding, 32 per review, 80 lines and 4,000 characters per span. Stale, foreign, clipped or altered source fails validation; locate the captured bytes or rescan instead of silently using newer source. Server-generated `support_verification` preserves checked identities and span hashes. Existing saved receipts remain historical evidence even when the working tree later changes. They verify source identity and quoted content, not the reasoning or independent agreement.

Reports separate declared confidence from this grounding through `confidence_assessment`. Missing legacy support remains unestablished; raw ratings and history are retained. Broad score blockers include partial review scope, missing current effectiveness evidence and an observed-burden declaration supported only by source. Use actual change/operational observations when available; source estimates remain useful without pretending to measure effort. Imported report presence alone does not establish its source, execution or scope. Resolve these gaps with appropriate evidence, not repeated reviews until a higher label appears.

For every burden rating, read `support.readiness` and its next useful evidence,
including for low/medium confidence or an unknown score. The inventory separates
cited mechanisms, applicable experience, matching cost observations, recurrence,
declared trace activities and a bound dimension challenge. Shared source citations
can identify related traces but do not establish their relevance. High project
support needs recurring dimension-specific experience or multiple distinct dated
matching cost observations; a single isolated timing supports workflow scope.
Even supported workflow confidence retains project-breadth and collection limits.
Inventory presence never assigns or promotes confidence. See [burden evidence](burden-evidence.md)
for import semantics and applicability checks.

## Verification and implementation

Choose proof appropriate to the full intended outcome. For testing, examine important public outcomes and credible failures at the real boundary; do not add duplicates to compensate for a missing run receipt. For extensibility, establish the actual variants, authors and compatibility needs before choosing a seam. For simplification, trace affected callers and preserve required security, data, error and concurrency behavior. More test files, fewer lines, a library adoption or a passing focused check cannot alone establish a rubric level.

Assessment authorizes advice, not executing assessed code or making changes. During separately authorized implementation, use focused checks while iterating, then complete the repository's required checks and affected system, contract or integration verification before claiming completion or pushing when authorized. Do not invent universal full-suite requirements for unrelated changes. Report unrun or unavailable checks and remaining risks. Rescan and review after changes; distinguish source improvement from changed judgment, new evidence and retargeting. Stop adding machinery when the intended target and its evidence are met.
